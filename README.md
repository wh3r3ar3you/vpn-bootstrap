# vpn-bootstrap

🚀 Первичная конфигурация для VPN-ноды на Debian/Ubuntu.

## О проекте

`vpn-bootstrap` — готовый сценарий первоначальной настройки выделенных VPN-нод. Он подготавливает чистый Debian или Ubuntu к высокой сетевой нагрузке, настраивает ядро и сетевой интерфейс, SSH, Docker, межсетевой экран и ежедневное атомарное обновление списков блокировки Traffic Guard.

Профиль рассчитан прежде всего на VPS с `virtio` и небольшим числом аппаратных очередей: входящий поток распределяется по ядрам процессора, очереди TCP и `fq` увеличиваются, а проблемный GRO автоматически отключается только при обнаружении драйвера `virtio_net`. Все настройки сохраняются после перезагрузки.

## ✨ Что делает проект

Проект устанавливает и настраивает:

- обновление системы и базовые пакеты для администрирования
- проверку базовых зависимостей и установку недостающих компонентов перед настройкой
- Docker через официальный скрипт установки
- дополнительное ядро XanMod LTS через официальный репозиторий APT
- Oh My Zsh, Powerlevel10k и плагины для `root`
- параметры `sysctl` для VPN-сценария
- постоянную настройку сетевого интерфейса с RPS/RFS, увеличенным `fq`, автоопределением `virtio`, управлением GRO и `irqbalance`
- дополнительный защитный профиль VPN с автоматическим подбором параметров `conntrack`, очередей и ограничений частоты через `iptables`
- интерактивную настройку имени узла, порта SSH и ключа SSH пользователя `root` (ключ можно пропустить)
- закрытие порта API ноды Remnawave для всех, кроме панели: по IP, подсети или домену
- запуск без вопросов через переменные окружения `BS_*`
- списки блокировки Traffic Guard на базе `ipset` и `iptables`
- ежедневное безопасное обновление списков блокировки через таймер `systemd`
- сохранение состояния межсетевого экрана и `ipset` через `netfilter-persistent`, если он доступен

## 📋 Требования

- Debian или Ubuntu
- запуск от `root`
- рабочий исходящий доступ в интернет
- `systemd`

## ▶️ Как запустить

### Вариант 1: установка одной командой

```bash
apt update && apt install curl -y && bash <(curl -fsSL https://raw.githubusercontent.com/wh3r3ar3you/vpn-bootstrap/main/install.sh)
```

Что делает эта команда:

- скачивает `install.sh` из GitHub
- при необходимости устанавливает минимальные зависимости для запуска установщика
- скачивает архив репозитория во временный каталог
- запускает `bootstrap.sh`

### Вариант 2: запуск из клонированного репозитория

```bash
chmod +x bootstrap.sh
./bootstrap.sh
```

Во время запуска скрипт спросит:

- имя узла
- порт SSH
- открытый ключ SSH для добавления в `/root/.ssh/authorized_keys` — можно пропустить
- устанавливать ли защитный профиль VPN
- устанавливать ли ядро XanMod LTS
- если выбран XanMod, выполнять ли автоматическую перезагрузку после завершения настройки
- адрес панели Remnawave — можно пропустить
- порт API ноды (`NODE_PORT`) — спрашивается, только если указан адрес панели

Если порт SSH оставить пустым, будет использован порт `22`. Если порт API оставить пустым, будет использован порт `2222`.

### Запуск без вопросов

Любой ответ можно передать переменной окружения — тогда вопрос не задаётся. Пустое значение переменной означает «пропустить» (для ключа SSH и адреса панели) или значение по умолчанию. Некорректное значение прерывает запуск с ошибкой.

| Переменная | Вопрос | Пример |
|---|---|---|
| `BS_HOSTNAME` | имя узла | `nl-1` |
| `BS_SSH_PORT` | порт SSH | `54777` |
| `BS_SSH_KEY` | открытый ключ SSH | `ssh-ed25519 AAAA... admin` или пусто |
| `BS_VPN_DEFENSE` | защитный профиль VPN | `д` / `н` |
| `BS_XANMOD` | ядро XanMod LTS | `д` / `н` |
| `BS_REBOOT` | перезагрузка после XanMod | `д` / `н` |
| `BS_PANEL_ADDRESS` | адрес панели | `panel.example.com` или `203.0.113.10,203.0.113.11` или пусто |
| `BS_PANEL_API_PORT` | порт API ноды | `2222` |

```bash
BS_HOSTNAME=nl-1 BS_SSH_PORT=54777 BS_SSH_KEY="ssh-ed25519 AAAA... admin" \
BS_VPN_DEFENSE=н BS_XANMOD=д BS_REBOOT=д \
BS_PANEL_ADDRESS=panel.example.com BS_PANEL_API_PORT=2222 \
bash <(curl -fsSL https://raw.githubusercontent.com/wh3r3ar3you/vpn-bootstrap/main/install.sh)
```

Переменные, которые не заданы, по-прежнему спрашиваются интерактивно.

## 🔑 Если ключ SSH пропущен

Пустой ответ на вопрос о ключе пропускает изменение `authorized_keys`. Дальше сценарий смотрит, есть ли у `root` хотя бы один ключ:

- ключи уже есть (например, их положил провайдер или cloud-init) — вход `root` разрешается только по ключу, пароль отключается, как и раньше
- ключей нет — `PasswordAuthentication`, `KbdInteractiveAuthentication`, `ChallengeResponseAuthentication` и `PermitRootLogin` не меняются, чтобы не потерять доступ к серверу; остальные настройки SSH (порт, `MaxStartups`, тайм-ауты) применяются

Во втором случае итоговая сводка напоминает добавить ключ и запустить сценарий повторно.

## 🔒 Доступ к API ноды только для панели

Нода Remnawave принимает команды панели на порту `NODE_PORT` (по умолчанию `2222`). Если указать адрес панели, сценарий закрывает этот порт для всех, кроме панели.

Адрес панели можно задать:

- IP-адресом: `203.0.113.10`
- подсетью: `203.0.113.0/28`
- доменом: `panel.example.com`
- списком через запятую: `panel.example.com, 203.0.113.10`
- IPv6-адресом или подсетью

Как это работает:

- адрес и порт сохраняются в `/etc/default/vpn-panel-access`
- `/usr/local/sbin/update-panel-access.sh` разрешает домены в A/AAAA-записи и собирает цепочку `VPN_PANEL_API_A` или `VPN_PANEL_API_B`: `ACCEPT` для `lo` и адресов панели, затем `DROP`
- в начало `INPUT` добавляется переход `-p tcp --dport <порт> -j VPN_PANEL_API_*`; остальные порты не затрагиваются
- новая цепочка собирается рядом со старой, переход переключается на неё, и только потом старая удаляется — порт не открывается ни на мгновение
- если доступен `ip6tables`, то же самое применяется к IPv6: без IPv6-адреса панели порт по IPv6 закрыт для всех
- `vpn-panel-access.timer` каждые 5 минут перепроверяет домены: если IP панели поменялся, правила пересобираются; если ничего не изменилось, правила не трогаются
- если домен не разрешился, действующие правила остаются как есть, а служба завершается с ошибкой до следующей успешной проверки
- правила сохраняются через `netfilter-persistent`, а `vpn-panel-access.service` восстанавливает их при загрузке

Изменить адрес или порт позже:

```bash
vim /etc/default/vpn-panel-access
/usr/local/sbin/update-panel-access.sh
```

Снять ограничение: оставить `PANEL_ADDRESS` пустым и запустить `/usr/local/sbin/update-panel-access.sh` — цепочки и переход будут удалены.

Проверка:

```bash
iptables -S | grep VPN_PANEL_API
systemctl list-timers vpn-panel-access.timer
journalctl -u vpn-panel-access.service -n 20 --no-pager
```

Правила живут в `iptables` и работают вместе с `mobile443` (таблица `ip mobile443` в `nftables`): пакет должен пройти обе проверки.

## 🛠 Что меняет сценарий

`bootstrap.sh`:

- задаёт имя узла и обновляет `/etc/hosts`
- пишет `/etc/sysctl.d/99-disable-ipv6.conf`
- пишет `/etc/sysctl.d/90-vpn-tuning.conf`, чтобы базовые значения применялись раньше защитного профиля
- применяет параметры через `sysctl -e -p`, чтобы неизвестные ключи старого ядра не прерывали настройку
- выполняет `apt-get update` и `apt-get -y upgrade`
- проверяет пакеты APT и устанавливает только отсутствующие через `apt-get`
- всегда ставит `ethtool` и `irqbalance`, включает распределение аппаратных IRQ
- определяет основной внешний интерфейс и устанавливает `/usr/local/sbin/apply-vpn-network-tuning.sh` вместе со службой `vpn-node-network-tuning.service`
- включает RPS/RFS на всех ядрах процессора, увеличивает `fq` и определяет драйвер интерфейса; для `virtio_net` отключает GRO, а на других драйверах не меняет его
- на многоочередном интерфейсе сохраняет корневой `mq` и меняет только дочерние очереди
- при выборе защитного профиля пишет `/etc/sysctl.d/99-vpn-defense.conf` и `/etc/modprobe.d/vpn-defense-conntrack.conf`
- при необходимости добавляет официальный репозиторий XanMod для APT и устанавливает `linux-xanmod-lts-x64v1/v2/v3` с учётом возможностей процессора
- если выбран XanMod и пользователь подтвердил автоматическую перезагрузку, перезагружает сервер после успешного завершения
- устанавливает и включает Docker
- настраивает Zsh-окружение для `root`
- при необходимости ставит `openssh-server` до изменения `sshd_config`
- создаёт `/root/.ssh` и `/root/.ssh/authorized_keys` с корректными правами
- добавляет переданный открытый ключ SSH без перезаписи существующих ключей; пустой ответ пропускает этот шаг
- обновляет `/etc/ssh/sshd_config`; если у `root` есть хотя бы один ключ, разрешает вход только по ключу и отключает вход по паролю; увеличивает очередь подключений до авторизации до `MaxStartups 100:30:200`, проверяет конфигурацию через `sshd -t` и только потом перезапускает SSH
- устанавливает скрипт обновления в `/usr/local/sbin/update-traffic-guard.sh`
- устанавливает и включает `traffic-guard-update.service` и `traffic-guard-update.timer`
- гарантирует наличие правил `DROP`/`REJECT` для набора `ipset blacklist` во входящем, исходящем и транзитном трафике
- добавляет те же ограничения по спискам блокировки в `DOCKER-USER`, если эта цепочка создана Docker
- добавляет `TCPMSS --clamp-mss-to-pmtu` в `mangle/FORWARD` для туннельного TCP-трафика
- если выбран защитный профиль VPN, добавляет помеченные правила `iptables` для ограничения SYN-запросов, фильтрации усиленного UDP-трафика и ограничения частоты эхо-запросов ICMP
- гарантирует наличие ровно одного правила блокировки эхо-запросов ICMP
- если указан адрес панели, пишет `/etc/default/vpn-panel-access`, устанавливает `/usr/local/sbin/update-panel-access.sh`, `vpn-panel-access.service` и `vpn-panel-access.timer` и закрывает порт API ноды для всех, кроме панели
- сохраняет правила межсетевого экрана через `netfilter-persistent save` только после успешного применения

## ⚙️ Какие sysctl-настройки включает скрипт

Сценарий записывает два файла:

- `/etc/sysctl.d/99-disable-ipv6.conf`
- `/etc/sysctl.d/90-vpn-tuning.conf`

После этого каждый файл применяется через `sysctl -e -p`.

При обновлении старые `/etc/sysctl.d/99-vpn-tuning.conf` и `/etc/sysctl.d/99-vpn-rps.conf` перемещаются в резервные копии. Это не позволяет им перезаписать защитный профиль после перезагрузки.

### Отключение IPv6

Включаются:

- `net.ipv6.conf.all.disable_ipv6=1`
- `net.ipv6.conf.default.disable_ipv6=1`

Это отключает IPv6 для обычных интерфейсов, но не затрагивает петлевой интерфейс.

### Сетевая настройка VPN-ноды

Включаются следующие параметры:

- `net.core.default_qdisc=fq`
- `net.ipv4.tcp_congestion_control=bbr`
- `net.ipv4.ip_forward=1`
- `net.ipv4.conf.all.forwarding=1`
- `net.ipv4.conf.default.forwarding=1`
- `net.ipv4.conf.all.rp_filter=0`
- `net.ipv4.conf.default.rp_filter=0`
- `net.ipv4.conf.all.src_valid_mark=1`
- `net.ipv4.conf.default.src_valid_mark=1`
- `net.core.rmem_max=67108864`
- `net.core.wmem_max=67108864`
- `net.core.rmem_default=262144`
- `net.core.wmem_default=262144`
- `net.core.optmem_max=4194304`
- `net.core.netdev_max_backlog=250000`
- `net.core.netdev_budget=600`
- `net.core.netdev_budget_usecs=8000`
- `net.core.somaxconn=32768`
- `net.core.rps_sock_flow_entries=32768`
- `net.ipv4.tcp_fastopen=3`
- `net.ipv4.tcp_rmem=4096 87380 67108864`
- `net.ipv4.tcp_wmem=4096 65536 67108864`
- `net.ipv4.tcp_mtu_probing=1`
- `net.ipv4.tcp_slow_start_after_idle=0`
- `net.ipv4.tcp_notsent_lowat=16384`
- `net.ipv4.tcp_tw_reuse=1`
- `net.ipv4.tcp_max_orphans=262144`
- `net.ipv4.tcp_fin_timeout=30`
- `net.ipv4.tcp_keepalive_time=600`
- `net.ipv4.tcp_keepalive_intvl=30`
- `net.ipv4.tcp_keepalive_probes=5`
- `net.ipv4.udp_rmem_min=8192`
- `net.ipv4.udp_wmem_min=8192`
- `net.ipv4.ip_local_port_range=1024 65535`
- `net.ipv4.tcp_max_syn_backlog=32768`
- `net.netfilter.nf_conntrack_max=1048576`
- `net.netfilter.nf_conntrack_tcp_timeout_established=7440`
- `net.netfilter.nf_conntrack_udp_timeout=60`
- `net.netfilter.nf_conntrack_udp_timeout_stream=180`

Что это означает на практике:

- `fq` включается как дисциплина очереди по умолчанию, что нужно для корректной работы BBR.
- `bbr` включается как алгоритм управления перегрузкой TCP. На многих VPN-нагрузках он лучше использует канал и стабильнее держит задержку по сравнению с классическими алгоритмами.
- `ip_forward=1` и `forwarding=1` включают маршрутизацию IPv4, без которой VPN-нода не сможет нормально пересылать клиентский трафик.
- `rp_filter=0` отключает строгую проверку обратного маршрута. Это важно для серверов с политиками маршрутизации, туннелями и VPN, где такая проверка может приводить к потере пакетов.
- `src_valid_mark=1` помогает корректно маршрутизировать пакеты с меткой `fwmark`, которую часто используют WireGuard и политики маршрутизации.
- `rmem_max` и `wmem_max` увеличивают максимальные размеры буферов приёма и передачи в ядре.
- `rmem_default` и `wmem_default` задают базовые значения буферов сокетов.
- `netdev_max_backlog=250000` увеличивает размер очереди входящих пакетов в ядре при высокой нагрузке.
- `somaxconn=32768` и `tcp_max_syn_backlog=32768` увеличивают очереди новых соединений и уменьшают вероятность кратковременных RST под всплеском нагрузки.
- `tcp_max_orphans`, `tcp_fin_timeout` и параметры проверки активности быстрее очищают зависшие TCP-сессии, не обрывая живые соединения слишком агрессивно.
- `tcp_fastopen=3` включает TCP Fast Open и для клиента, и для сервера.
- `tcp_rmem` и `tcp_wmem` расширяют диапазоны автонастройки TCP-буферов.
- `tcp_mtu_probing=1` включает подбор MTU, что помогает при ошибках определения MTU на маршруте и пропаже пакетов без ответа.
- `nf_conntrack_*` увеличивает таблицу `conntrack` и сокращает слишком длинные тайм-ауты для нагрузки выходной VPN-ноды.

Итог: после установки сервер получает производительный сетевой профиль для VPN и туннельной нагрузки вместо консервативных настроек дистрибутива по умолчанию.

## Сетевой интерфейс, RPS/RFS и fq

`vpn-node-network-tuning.service` запускается после появления сети и при каждой загрузке:

- находит основной интерфейс через маршрут по умолчанию
- определяет драйвер через sysfs, а при необходимости через `ethtool -i`
- включает RPS на всех доступных ядрах процессора и таблицу потоков RFS на `32768` записей
- автоматически отключает `gro` и `rx-gro-hw` только для `virtio_net`
- ставит `fq` с `limit 100000`, `flow_limit 1000` и `buckets 8192`
- не заменяет корневой `mq` на многоочередном интерфейсе, а применяет `fq` отдельно к каждой очереди передачи

Настройки можно переопределить в `/etc/default/vpn-node-network-tuning`:

```bash
VPN_PRIMARY_INTERFACE=ens3
VPN_RPS_FLOW_ENTRIES=32768
VPN_DISABLE_GRO=auto
VPN_FQ_LIMIT=100000
VPN_FQ_FLOW_LIMIT=1000
VPN_FQ_BUCKETS=8192
```

`VPN_DISABLE_GRO=auto` используется по умолчанию. Значение `1` принудительно отключает GRO на любом драйвере, а `0` запрещает скрипту менять GRO. После изменения перезапустите `vpn-node-network-tuning.service`.

## 🛡 Защитный профиль VPN

Защитный профиль VPN выключен по умолчанию и включается отдельным интерактивным вопросом.

Если выбрать `да`, сценарий:

- определяет объём оперативной памяти и число ядер процессора
- подбирает `nf_conntrack_max`, число корзин хеш-таблицы `conntrack`, `somaxconn`, `tcp_max_syn_backlog` и `netdev_max_backlog`
- пишет `/etc/sysctl.d/99-vpn-defense.conf`
- пишет `/etc/modprobe.d/vpn-defense-conntrack.conf`, чтобы сохранить размер хеш-таблицы `conntrack` после перезагрузки
- применяет доступные sysctl сразу через `sysctl -e -p`
- создаёт или пересоздаёт цепочки `VPN_SYN_LIM` и `VPN_UDP_AMP`
- добавляет в `INPUT` только правила с меткой `vpn-defense`
- ограничивает TCP SYN на портах `80,443,8443` через `hashlimit` отдельно для каждого исходного IP-адреса
- ограничивает усиленный UDP-трафик с исходных портов `19,53,123,389,1900,11211,5060,1194`
- пропускает до 30 эхо-запросов ICMP в секунду со всплеском до 60, а лишние отбрасывает
- сохраняет правила межсетевого экрана через `netfilter-persistent save`

## 🧬 Ядро XanMod LTS

Сценарий может дополнительно установить ядро XanMod LTS. По умолчанию выбран ответ `нет`, потому что смена ядра вступает в силу только после перезагрузки.

Если выбран XanMod, сценарий отдельно спросит, выполнять ли автоматическую перезагрузку после успешной установки и настройки сервера. По умолчанию она выключена.

Если выбрать `да`, сценарий:

- проверит, что система `x86_64`
- проверит кодовое имя дистрибутива по списку, поддерживаемому репозиторием XanMod для APT
- добавит `/etc/apt/keyrings/xanmod-archive-keyring.gpg`
- добавит `/etc/apt/sources.list.d/xanmod-release.list`
- определит поддерживаемый процессором уровень x86-64 psABI через загрузчик glibc
- установит один из пакетов `linux-xanmod-lts-x64v1`, `linux-xanmod-lts-x64v2` или `linux-xanmod-lts-x64v3`

XanMod LTS уместен для VPN-ноды, если нужны более свежая сетевая подсистема ядра, BBRv3, MGLRU и дополнительные исправления планировщика и сети. Штатное ядро остаётся в GRUB как резервный вариант.

## 🧱 Как обновляется Traffic Guard

Скрипт обновления использует безопасную атомарную схему:

1. создаёт или использует активный `ipset` `blacklist`
2. создаёт уникальный временный `ipset` вида `blacklist_new_<pid>`
3. скачивает списки блокировки через `curl -fsSL`
4. очищает данные от пустых строк, комментариев и дублей
5. пропускает некорректные записи
6. заполняет временный набор через `ipset restore`
7. выполняет `ipset swap <temp_set> blacklist`
8. удаляет временный набор

Такой подход не снимает блокировку даже на короткий момент. Если загрузка, проверка или заполнение нового набора завершаются ошибкой, активный `blacklist` остаётся без изменений.

Скрипт обновления получает блокировку через `flock`, поэтому ручной запуск не конфликтует с запуском по таймеру `systemd`.

Служба `systemd` ограничена необходимым набором возможностей ядра и разрешённых путей записи. Скрипт получает только права, нужные для работы с `ipset`, `iptables`, журналом, файлом блокировки и сохранением состояния межсетевого экрана.

Для контейнерного сценария скрипт также восстанавливает правила списков блокировки в `DOCKER-USER`, если Docker уже создал эту цепочку.

Логи обновления пишутся в `/var/log/traffic-guard-update.log`.

## 🔎 Как проверить таймер и службу

```bash
systemctl status traffic-guard-update.timer
systemctl list-timers traffic-guard-update.timer
systemctl status traffic-guard-update.service
```

## 🔁 Как обновить списки вручную

```bash
/usr/local/sbin/update-traffic-guard.sh
```
